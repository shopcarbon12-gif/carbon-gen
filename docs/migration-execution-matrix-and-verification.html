D) VERIFICATION HTML REPORT (MANDATORY after EVERY batch you execute)
- Create a NEW file following the structure in the user’s doc: migration-execution-matrix-and-verification.html → section “Verification HTML report”.

E) If blocked
- State blocker (permissions, missing .env, network, Coolify down, etc.); list exact next step for human.

F) INVENTORY REPORTS (when user says Windows dev inventory + mirror sync are done)
- Expect under backup-from-windows-c/: inventory/ with master CSV (L1–L3+L5 from dev-disk-inventory.ps1), git-triage sidecar if separate, and WinDirStat/WizTree exports for BOTH C: and D: (mandatory L4 companions).

- Still read-only on backup-from-windows-c/ unless user orders changes.

This rule is non-negotiable. Partial completion without a report is considered incomplete work.

Verification HTML report — required structure

Use this outline for every batch (Ubuntu agent or Windows agent). Save as a new dated file each time.

  • <h1> Title: Migration verification — <YYYY-MM-DD> — batch <id>
  • Meta block: Agent role (Windows carbon-gen / Ubuntu SSH / …), repo path, git commit hash if applicable, duration.
  • User request (verbatim): quote what they ordered for this batch.
  • Checklist table: columns: Task | Expected | Result (DONE/NOT DONE/BLOCKED) | Evidence | Matches ask (YES/NO)
  • Commands run: bullet list; for long output, “summary + path to full log file” on disk (no secrets).
  • Filesystem evidence: important paths, du -sh or Windows equivalent, file counts where relevant.
  • URLs / HTTP: status codes from curl or browser test; note if skipped and why.
  • Deviations: anything done differently from the ask; user impact.
  • Follow-ups for user: only concrete items you cannot do without them.
  • Sign-off line: “Report complete: YES” or “Partial: reason …”
Styling: You may reuse the same CSS as migration-ubuntu-master-plan.html for readability; content matters more than theme.

Hard prohibitions (avoid common agent mistakes):

  • No Docker Desktop → VM “transfer”: Do not instruct copying Docker Desktop’s internal disk, WSL2 Docker data, or image store into Ubuntu. Install Docker Engine in the guest; docker compose up re-pulls images. Data: pg_dump / restore only if preserving local DB — §10.8b.
  • No BIOS/installer automation: Do not claim an API can press firmware keys, click Ubuntu install wizards, or enter passwords in the VM — see §0b stop box.
  • No long-term host junctions / shared-folder workspaces: Daily git work lives under ~/dev/… inside the VM disk, not on /media/sf_* permanently — §15.
  • Separate production from dev: Live sites and prod Postgres are on Coolify (VPS). VM docker compose is local dev only — §13.0.
  • One Postgres port in the VM: carbon-gen and CarbonWMS compose both use host 5432 by default — do not run both stacks simultaneously without changing one published port.
  • Guest Additions source: Use Devices → Insert Guest Additions CD from the host VirtualBox version; do not install virtualbox-*_Ubuntu_*_amd64.deb from D:\downloads inside the guest (wrong use case).
  • No premature deletion on Windows: Do not advise deleting Windows project trees (or “move = delete”) until the user has fully verified the Linux workflow. Required sequence: zip-archive everything to D: (dated archives), keep originals until sign-off — §15 archive policy.

Why (C: space)

Goal: stop C:\ from filling with dev caches (node_modules, Docker layers, IDE data). The VirtualBox host still needs a fixed ~300+ MB on C: (program under C:\Program Files\Oracle\VirtualBox + kernel drivers under C:\Windows\System32\drivers) — that cannot move to D:. The VM disk (.vdi) and default machine folder live on D: (e.g. D:\VMs\VirtualBox); node_modules, Gradle, Android SDK, Linux Cursor data, and Docker images grow inside that VDI (i.e. on D: from Windows’ view), not as endless scatter on C:.

Automation (repo): scripts/virtualbox-end-to-end.ps1 (download + sync + elevate) · scripts/install-virtualbox-d-drive.ps1 · scripts/download-virtualbox-installers.ps1

Mandatory practices

  1. Repos in the VM. Keep carbon-gen, CarbonWMS, and other projects under e.g. ~/projects, ~/dev, or /srv/... inside Ubuntu. git push regularly. Git + remote is the source of truth — not “files only on one disk.” Disk experiments on C: or D: must not equal product loss.
  2. Linux-native dev stack in Ubuntu. Run Node, Docker Engine, Flutter, Android tooling, builds in the guest so node_modules and Docker images grow inside the VDI, not on Windows C:.
  3. Cursor only in Ubuntu. Use Cursor for Linux inside the VM for daily Carbon work so Windows C: does not absorb Cursor caches. After that habit sticks, you can uninstall or stop using Cursor on Windows (see §15).
  4. Production = Coolify (VPS). The live sites for carbon-gen and CarbonWMS run as Coolify-managed containers with linked Postgres and Traefik — not as “whatever is in your VM.” After git push, deploy from your Coolify workflow (see §13.0).
  5. Archive on D:, do not delete early. When retiring Windows working copies, zip-archive everything to D: (dated archives) before any deletion. Keep originals until Linux is fully verified — §15.
Deleting the VM disk is not “like clearing a cache.” Removing the .vdi deletes the whole guest — including any work not pushed to Git. Snapshots help rollback; Git + push protects your app and site source.

START HERE — Full install & move Carbon projects (you are at §5)

Host: If VirtualBox is not installed yet, prefer scripts/virtualbox-end-to-end.ps1 from the carbon-gen repo (downloads to D:\downloads, default VM folder on D:\VMs\VirtualBox, Oracle MSI to default C: path — see Canonical plan). Otherwise use Phase B below. Your D:\downloads folder may already contain installers (Ubuntu ISO, Flutter, Node 20 Linux, Cursor .deb, Android Studio, cmdline-tools, VirtualBox Win + Extension Pack, get-docker.sh, etc.). Follow the phases in order. BIOS keys and Ubuntu installer clicks are you only.

Phase A — §5 Before you install (Windows host) you only

  1. BIOS / UEFI virtualization. Restart the PC → enter firmware setup (often Del, F2, F10, or Esc at boot) → find and Enable Intel VT-x / AMD SVM / AMD-V. Save and exit.
  2. Free RAM. Close browsers, Docker-heavy stacks, and other VMs before starting VirtualBox the first time (~16 GB host RAM total).
  3. Hyper-V vs VirtualBox. If the VM fails with a virtualization error: open Turn Windows features on or off and note whether Hyper-V / Virtual Machine Platform / Windows Hypervisor Platform are on. Search the web for Windows 11 VirtualBox Hyper-V and your VirtualBox version — follow Oracle/Microsoft guidance (sometimes “Windows Hypervisor Platform” helps; sometimes you must disable conflicting features).
  4. Windows Update. Install pending updates and reboot once.
Checkpoint: You are ready for Phase B when you have rebooted after any BIOS change and Windows is idle enough to install software.

Phase B — Install VirtualBox on Windows (host)

  1. Open File Explorer → go to D:\downloads.
  2. Double-click VirtualBox-7.2.6a-172322-Win.exe (or run scripts/install-virtualbox-d-drive.ps1). Accept UAC. Prefer default C: install if a custom D: path fails (see §6).
  3. Reboot if the installer asks.
  4. Start Oracle VM VirtualBox from the Start menu.
  5. Menu File → Preferences → General → set Default Machine Folder to D:\VMs\VirtualBox (create the folder if needed).
  6. Menu File → Tools → Extension Pack Manager → Install → select D:\downloads\Oracle_VirtualBox_Extension_Pack-7.2.6.vbox-extpack → agree to license.
Checkpoint: VirtualBox opens without errors; Extension Pack shows as installed for 7.2.6.

Phase C — Create the VM and attach the Ubuntu ISO

  1. In VirtualBox click New. Name: UbuntuDev (or similar). Type: Linux, Version: Ubuntu (64-bit).
  2. RAM: 6144 MB (6 GB) recommended on your hardware; 8192 MB only if the host stays responsive.
  3. Create a VDI, dynamically allocated, size 200 GB (or at least 128 GB).
  4. Select the VM → Settings → System → Processor: 2 CPUs. Display: max video memory.
  5. Storage → empty IDE/SATA optical drive → choose disk file → D:\downloads\ubuntu-24.04.4-desktop-amd64.iso.
Checkpoint: VM exists; ISO is attached; no start yet until you are ready for a long install.

Phase D — Install Ubuntu inside the VM you only

  1. Click Start on the VM. The Ubuntu installer should appear.
  2. Choose Install Ubuntu → keyboard → optional third-party drivers → Erase disk and install Ubuntu (this is only the virtual disk).
  3. Create your Linux username and password. Wait for completion → Restart → if asked, press Enter to remove “installation medium” (VirtualBox usually ejects the ISO).
Checkpoint: You can log in to the Ubuntu desktop inside the VM.

Phase E — Guest Additions (you only — inside Ubuntu + one host menu)

What this fixes: smooth mouse (no “captured” feeling), auto-resize when you drag the VM window, shared-folder support (vboxsf), better clipboard integration, and sometimes time sync. Do Phase E before Phase F if you rely on shared folders.

Same content, deeper reference: §9 — Guest Additions (below). This Phase E block is the step-by-step you follow now.

E.0 — Preconditions (check these first)

  • Ubuntu is running and you are logged in to the desktop (not stuck at login screen).
  • The VirtualBox window for UbuntuDev is active — the menu bar says File / Machine / View / Input / Devices / Help (host menus), not only Ubuntu’s own top bar inside the guest.
  • Extension Pack is installed on Windows (Phase B). Without it, some Devices menu actions fail.
  • Let any first-boot “Software Updater” finish or postpone it — avoid running a full distro upgrade at the same moment as Guest Additions build (reduces kernel mismatch errors).

E.1 — Insert the Guest Additions CD (on the host, one click path)

  1. Click the VirtualBox VM window title bar or inside the guest so VirtualBox has focus (not only your Windows taskbar).
  2. In the top menu of that window (Oracle VM VirtualBox), open Devices.
  3. Click Insert Guest Additions CD image…
    • If it is grayed out: ensure the VM is Running. If still grayed out, try Devices → Optical Drives → Remove disk from virtual drive, wait a few seconds, then Insert Guest Additions CD image again.
    • If you see an error about unable to mount: shut down Ubuntu gracefully, open VM Settings → Storage, ensure the virtual optical drive is empty or set to “Host Drive” as appropriate, start VM, retry.
  4. Within a few seconds, Ubuntu may pop up “VBox_GAs_…” or “CD / Removable Media” — you can use that, or continue in the terminal in E.3–E.4 (recommended).

E.2 — Install kernel headers & build tools (Ubuntu Terminal)

Open Terminal in Ubuntu (Ctrl+Alt+T on most setups). Run exactly:

sudo apt update
sudo apt install -y build-essential dkms linux-headers-$(uname -r)
  • Enter your Linux password when prompted (characters do not echo — that is normal).
  • Wait until the command completes with no red “E:” errors. If linux-headers-$(uname -r) fails, reboot Ubuntu once, run sudo apt update again, retry the same install line — your kernel may have updated after first boot.

E.3 — Locate the mounted Guest Additions disc

In Terminal, list your user’s media mount point (Ubuntu Desktop usually mounts CDs under /media/<yourusername>/):

ls /media/$USER/

You should see a folder whose name starts with VBox_GAs_ (version numbers match your VirtualBox, e.g. 7.2.x). If you see nothing:

  • Repeat E.1 (Insert Guest Additions CD image).
  • Open the Files app → look under Other Locations or a disc icon on the sidebar → note the path shown in the address bar.

E.4 — Run the Linux installer script

cd /media/$USER/VBox_GAs_*
sudo ./VBoxLinuxAdditions.run
  • The installer prints progress. A successful run ends without a fatal error; you may see warnings — note the last 10–15 lines if it fails.
  • If it says kernel headers or gcc missing: go back to E.2, install packages, run E.4 again.
  • Do not install the file virtualbox-*_Ubuntu_*_amd64.deb from D:\downloads inside the guest — that package is for running VirtualBox on bare-metal Ubuntu, not for Guest Additions inside a VM.

E.5 — Reboot the guest (required)

  1. When the installer finishes, run: 
    sudo reboot
    or use Ubuntu’s Power Off / Restart menu inside the VM.
  2. After reboot, log in again.

E.6 — Verify it worked

  • Resize test: Drag the corner of the VirtualBox window on Windows. The Ubuntu desktop resolution should adjust without huge black borders (may take a second).
  • Mouse test: Move the pointer across the guest edge — it should feel integrated, not “trapped” inside the VM.
  • Optional terminal check: 
    lsmod | grep -E 'vboxguest|vboxsf'
    You should see modules such as vboxguest (and after shared folders are used, vboxsf).
Checkpoint E: Guest Additions installed, guest rebooted, window resize works. On Windows you can run powershell -ExecutionPolicy Bypass -File scripts/verify-virtualbox-phases-a-through-e.ps1 (from the carbon-gen repo) while the VM is running — Phase E is OK only if reported Guest Additions match the host (e.g. 7.2.x with VirtualBox 7.2.6). Proceed to Phase F (shared folders + vboxsf user group).

E.6b — Host reports wrong Guest Additions version (e.g. 6.0.x with VirtualBox 7.2.x)

If Windows reports Additions version: 6.0.0 (or anything not matching your host’s 7.2.x), Ubuntu is almost certainly using the wrong packages (virtualbox-guest-* from Ubuntu’s repos) instead of Oracle’s installer from the CD. That breaks resize/shared folders for your real host version.

  1. In Ubuntu: 
    dpkg -l | grep -i virtualbox-guest
    If you see packages, remove them, e.g.: 
    sudo apt remove -y virtualbox-guest-utils virtualbox-guest-x11 virtualbox-guest-dkms
    (add any other virtualbox-guest-* lines apt lists.)
  2. Re-run E.1–E.5 using Devices → Insert Guest Additions CD image from your 7.2.6 host, then sudo ./VBoxLinuxAdditions.run, reboot.
  3. On Windows, re-check with: scripts/verify-virtualbox-phases-a-through-e.ps1 — Guest Additions major.minor should match 7.2.

E.7 — If something fails (common fixes)

SymptomWhat to do
“Insert Guest Additions CD” does nothingRepeat E.1; confirm Extension Pack on host; remove virtual disc then insert again.
sudo: ./VBoxLinuxAdditions.run: command not foundWrong folder — run ls /media/$USER/, cd into the VBox_GAs_* directory, ls to confirm VBoxLinuxAdditions.run exists.
Build errors about kernel / headersComplete E.2; ensure kernel matches: uname -r and installed linux-headers-$(uname -r); reboot and retry.
Screen still doesn’t resizeView menu on host: try Auto-resize Guest Display (VirtualBox 7). Reboot guest again after GA install.

Phase F — Shared folders = transport only (not your final workspace)

Your goal is a true move to Linux: project files, Cursor usage, and Docker-based dev should ultimately live only inside the VM disk (e.g. under ~/dev/, ~/.config/), not mirrored from Windows and not via junctions/symlinks on the host. Shared folders are a temporary pipe to copy data in; after Linux builds work, you zip-archive the Windows trees to D: and keep them until full verification — do not delete Windows originals early (see §15 archive policy).

Option 1 (simplest): In VirtualBox Settings → Shared Folders, add Folder Path D:\downloads, Folder Name downloads, Auto-mount + Make Permanent. Typical mount: /media/sf_downloads. Use it to copy installers into the guest (e.g. ~/installers or /opt), not to build daily from the share.

Option 2: Create D:\DevShared, share it as devshared, and copy only the smaller Linux installers into it from D:\downloads.

Files you will use inside Linux from the share: node-v20.20.2-linux-x64.tar.xz, flutter_linux_3.41.6-stable.tar.xz, cursor-linux-x64.deb, anydesk_8.0.2_amd64.deb (remote desktop), commandlinetools-linux-14742923_latest.zip, optional android-studio-panda2-linux.tar.gz, get-docker.sh. See D:\downloads\ANYDESK-README.txt for AnyDesk install commands. Do not install virtualbox-7.2_…noble_amd64.deb inside the guest — that is for running VirtualBox on bare-metal Ubuntu, not for a VM guest.

In Ubuntu terminal, add your user to the share group (then log out and back in):

sudo usermod -aG vboxsf $USER

After re-login, the share is often at /media/sf_devshared (if empty, reboot the VM once).

Phase G — Install toolchain inside Ubuntu (order matters)

Run updates, base packages, Git identity, Node 20, Flutter, Android cmdline tools path, Cursor .deb, Docker — the detailed commands are in §10 of this guide. Short order:

  1. sudo apt update && sudo apt install -y git curl unzip xz-utils zip openjdk-17-jdk build-essential
  2. Expand Node from the shared folder under /opt or your home; add bin to PATH (see §10.7).
  3. Expand Flutter tarball to ~/development/flutter; add to PATH; run flutter doctor.
  4. Install Android cmdline tools + SDK paths (§10.3 / Android docs) or install Android Studio from the copied .tar.gz.
  5. sudo apt install -y ./cursor-linux-x64.deb from the folder where you copied the .deb (or sudo dpkg -i … then sudo apt -f install if dependencies complain).
  6. Docker: prefer official Ubuntu steps; if you use get-docker.sh, read it first, then sudo sh get-docker.sh, then add user to docker group and re-login.

Phase H — Put carbon-gen & CarbonWMS into the VM (then move, don’t mirror)

Best method (clean): In Ubuntu, mkdir -p ~/dev and git clone from your remote (§10.2). That creates a single home on Linux; you then stop using the Windows trees for daily work and archive them to D: as zip when ready — no deletion on Windows until §15 verification sign-off.

Copy method (one-time import): Use shared folder myprojects → /media/sf_myprojects only to cp -a (or rsync -a) into ~/dev/carbon-gen and ~/dev/carbon-warehouse-management. Remove node_modules before or after copy; run npm ci on Linux. Do not keep editing the copy under /media/sf_* as your daily workspace — that would be mirroring Windows. After npm run build / smoke tests pass, follow §15: zip-archive Windows originals to D:, do not delete yet.

Port conflict: Both repos use Postgres on host port 5432 in their compose files. Do not run both stacks at once unless you change one file to e.g. 5433:5432.
Where automation must stop: No MCP or API can press BIOS keys, click Ubuntu’s “Install” wizard, or type your passwords inside the VM. If any step fails, note the exact error text (or screenshot), which phase you were in, and search or ask with that message — most issues are virtualization settings, shared-folder group membership, or Docker/Node PATH.

§15 — Move everything to Linux (not mirror, not junction)

Use this checklist when Linux is installed and tooling works. Goal: canonical copies on the guest disk only; no ongoing sync, no host junctions pointing at project roots.

Archive first — no deletion until verified (locked policy). You are not deleting Windows project folders as the default next step. After Linux smoke tests pass, zip-archive the full Windows trees (carbon-gen, CarbonWMS, and anything else you rely on) to D:, e.g. D:\archive-pre-linux-verify\ with dated names (carbon-gen-YYYY-MM-DD.zip, carbon-wms-YYYY-MM-DD.zip). Keep the originals on disk until you have explicitly confirmed everything behaves as expected in the VM (and backups are tested if you care). Only then may you delete Windows copies — or keep the zips indefinitely. Assistants must not recommend deleting before this archive + verification step.

What “move” means here

  • Move = copy into the VM filesystem → verify (build, tests, Docker compose, Cursor opens repo) → zip-archive old Windows paths to D: → only after full verification, optionally delete originals (or keep zips only).
  • Not mirror: Don’t treat /media/sf_downloads or /media/sf_myprojects as the place you git commit every day; copy out to ~/dev/… first.
  • Not junction/symlink on Windows: No NTFS junction from C:\… to D:\Projects\… as a substitute for living on Linux — you want data inside the .vdi.

Checklist — projects (Carbon-gen, CarbonWMS, other repos)

  1. Ensure trees live under e.g. ~/dev/carbon-gen, ~/dev/carbon-warehouse-management, and any other repos under ~/dev/<name>.
  2. Fresh npm ci (and flutter pub get for WMS mobile) on Linux; fix any env files (.env, .env.local) from templates — do not commit secrets.
  3. Run smoke checks (e.g. npm run dev, docker compose up, flutter doctor) from the Linux paths only.
  4. Required: Create D:\archive-pre-linux-verify\ (or similar on D:). Zip-archive each Windows project tree you are retiring from daily use — full folders, not cherry-pick — with date in the filename. This is your safety net until verification is complete.
  5. Do not delete D:\Projects\My project\carbon-gen, …\carbon-warehouse-management, or other migrated repos on Windows until you have finished verifying Linux and are satisfied the zips are good. After sign-off, you may delete originals, or keep both zips and folders until disk pressure forces a choice.
  6. Remove or disable VirtualBox shared folders for those paths if you no longer need import (optional cleanup).

Checklist — Cursor (Windows → Linux)

  1. Install and open Cursor in Ubuntu (you already have cursor-linux-x64.deb).
  2. Manually copy what you care about from Windows: e.g. %APPDATA%\Cursor\User\settings.json, keybindings.json, snippets\, and %USERPROFILE%\.cursor\mcp.json into the Linux Cursor config locations (under ~/.config / Cursor’s docs — paths differ slightly from Windows).
  3. Re-install extensions in Linux Cursor: Dart-Code.dart-code, Dart-Code.flutter, plus any others from your repo recommendations.
  4. After Linux is your daily driver for Carbon work, you may uninstall Cursor on Windows or stop using it — that’s the “move” of your editor habit, not a file mirror.

Checklist — Docker

  1. Use Docker Engine + compose plugin inside Ubuntu for carbon-gen / CarbonWMS Postgres stacks. See §10.8b — you do not copy Docker Desktop’s ~10 GB into Ubuntu; you install Engine fresh and re-pull images.
  2. Windows Docker Desktop images/volumes are not the same disk as Linux. Usually you re-pull images with compose on Linux rather than migrating volumes. If you had critical local DB data on Windows, export with pg_dump first, then import in Linux.
  3. When everything runs in the VM, quit Docker Desktop on Windows or uninstall it if you want zero Docker on the host.

Checklist — installers & D:\downloads

  1. After Linux copies of Node tarball, Flutter, Android tools, etc. are extracted and verified, you may keep D:\downloads as a cold archive or delete duplicates to save space — your choice.
VirtualBox stays on Windows until you someday switch to Linux bare metal. Only the projects, Cursor data, and Docker dev workflow move into the guest in the sense above.

1. Your D: drive (analysis)

Volume letter: D: File system label: DATA File system: NTFS Total size: ~931 GB (about 1,000,006,887,014 bytes) Free space: ~707 GB (about 758,649,917,440 bytes) Host RAM (snapshot): ~16 GB total — plan the VM memory carefully (see section 7).
Verdict: D: has plenty of room for a large dynamically allocated virtual disk (Android SDK, emulators, Gradle caches, and Flutter can grow to tens of gigabytes over time). The limiting factor on your snapshot is RAM, not disk space.

2. What fits your need (VirtualBox + Linux)

VirtualBox

Oracle VirtualBox 7.x (current stable from virtualbox.org) matches your goal: run a full Linux desktop where Cursor, Flutter, Gradle, and the Android SDK all live inside the virtual disk file on D:. Windows C: is not where that bulk data grows.

VirtualBox itself may still write small configuration data under your Windows user profile (often on C:). That is normal and tiny compared to Android SDK + emulators. You avoid the big growth on C: by storing the VM disk (.vdi) on D: and by not mapping shared folders to C:\.

Which Linux?

Ubuntu Desktop LTS (24.04 LTS or 22.04 LTS) is the best default for beginners with Flutter and Android tooling: huge community, clear docs, and straightforward drivers for VirtualBox Guest Additions.

  • Pick 24.04 LTS if you want the newest long-term stack.
  • Pick 22.04 LTS if you hit a rare compatibility issue and want maximum “battle-tested” references online.

Alternatives (Fedora, Debian) work, but troubleshooting Android + Flutter on a first VM is easier on Ubuntu LTS.

3. Healthy folder layout on D:

Use a predictable structure so backups and upgrades are simple:

D:\VMs\VirtualBox\

Default machine folder (VirtualBox setting). All .vdi / snapshot files live here — this is where the space is used.

D:\VMs\ISOs\

Store the Ubuntu .iso installer (optional after install; you can delete to save space).

D:\DevShared\

Optional single Windows folder to share into Linux if you want file exchange. Keep it on D: only — never point a share at C:\ if your goal is to keep C: clean.

5. Before you install (BIOS & Windows)

  1. Enable virtualization in firmware (BIOS/UEFI). Names vary: Intel VT-x, AMD-V, SVM Mode. If VirtualBox says acceleration is unavailable, this is the first place to check.
  2. Close heavy apps before first VM boot. With ~16 GB host RAM, Android emulator + IDE + browser together can exhaust memory.
  3. Hyper-V / other hypervisors: If VirtualBox fails to start a 64-bit guest or complains about virtualization, search for your Windows version + “VirtualBox Hyper-V” — fixes vary (Windows Hypervisor Platform, disabling conflicting features, or updating VirtualBox). Do not panic; this is common on Windows 10/11.
  4. Windows updates: Install pending updates; reboot. Reduces odd driver conflicts.

6. Install VirtualBox (host: C: app · VMs on D:)

Oracle MSI reality: A custom install directory on D: often fails (CheckTargetDir / invalid name). The supported approach in this repo is scripts/install-virtualbox-d-drive.ps1: program on C:, default machine folder on D:\VMs\VirtualBox. Same idea as Canonical plan.
  1. Download the Windows installer from the VirtualBox Downloads page (link above), or use scripts/download-virtualbox-installers.ps1.
  2. Run the installer to the default location on C: if a custom D: path fails; then set Default Machine Folder to D: (next steps). Optional: try D: only if the wizard accepts it without errors.
  3. Finish the install. Reboot if the installer requests it.
  4. Open VirtualBox. Go to File → Preferences → General. Set Default Machine Folder to D:\VMs\VirtualBox (create the folder first if needed).
  5. Optional: install the Extension Pack (same version as VirtualBox): File → Tools → Extension Pack Manager → Install. Match versions exactly.
Network drivers prompt: VirtualBox may install virtual network adapters. Windows may show a firewall prompt — allow for “Private” networks if you trust your home network.

7. Create the Linux VM

These values are tuned for your ~16 GB RAM host and Flutter + Gradle + Cursor + Android.

  1. VirtualBox → New. Name: UbuntuDev. Type: Linux. Version: Ubuntu (64-bit).
  2. Memory: Use 6144 MB (6 GB) as a safer default. If you rarely run anything heavy on Windows while developing, you can try 8192 MB (8 GB); if the host freezes, reduce VM RAM.
  3. Hard disk: Create a virtual hard disk now. Format: VDI. Storage: Dynamically allocated (grows as needed). Size: 128 GB minimum; 200 GB is comfortable for Android SDK + a few system images + Gradle over time. Your D: free space supports this.
  4. Before first boot: select the VM → Settings:
    • System → Processor: 2 CPUs (try 3 only if the host stays responsive).
    • Display → Video Memory: increase to the maximum allowed (often 128 MB).
    • Storage: under the empty optical drive, click the disk icon and Choose a disk file → select your Ubuntu ISO from D:\VMs\ISOs\.
Android emulator inside a VM (nested virtualization): Often slow or unsupported in VirtualBox. Beginners should plan on a physical Android phone with USB debugging for day-to-day Flutter runs, or accept very slow emulators. Building APKs with Gradle still works without a running emulator.

8. Install Ubuntu inside the VM

  1. Start the VM. Ubuntu installer appears. Choose Install Ubuntu.
  2. Keyboard layout: your language.
  3. Updates: you can check “Install third-party software” for drivers (Wi‑Fi, etc.) — useful in VMs.
  4. Disk: Erase disk and install Ubuntu (this refers to the virtual disk only, not your Windows D: partition).
  5. Create your user name and password. Use a strong password.
  6. Wait for completion → restart when asked → press Enter if prompted to remove installation medium (VirtualBox may auto-eject ISO).

9. Guest Additions (recommended)

Full step-by-step (what to click, what to type, how to verify): use Phase E — Guest Additions in the START HERE runbook above. The summary below is a shortcut checklist only.

Why install: Better mouse integration, auto-resize of the guest desktop when you resize the VirtualBox window, shared folders (vboxsf), and optional clipboard improvements.

  1. Host menu: With the Ubuntu VM focused, Devices → Insert Guest Additions CD image.
  2. Guest prep: sudo apt update then install build-essential, dkms, and linux-headers-$(uname -r) (exact block in Phase E).
  3. Guest install: cd /media/$USER/VBox_GAs_* then sudo ./VBoxLinuxAdditions.run.
  4. Reboot: sudo reboot — then confirm resize + mouse (Phase E.6).
If the installer complains about missing headers or compiler, install the packages in Phase E.2 and run VBoxLinuxAdditions.run again. Do not install the host-style virtualbox-*_Ubuntu_*_amd64.deb inside the VM for this purpose.

10. Cursor, Flutter, Gradle, Android SDK (inside Linux)

Work in this order: base packages → Java → Android tooling → Flutter → Cursor.

10.1 Base packages (terminal in Ubuntu)

sudo apt update
sudo apt install -y git curl unzip xz-utils zip openjdk-17-jdk build-essential

Verify Java: java -version (should mention 17).

10.2 Git (version control — required)

carbon-gen and carbon-warehouse-management are Git repositories. You need Git inside the Ubuntu VM to clone, branch, commit, and pull/push.

The command above already installs Git (git is in the apt install list). Verify:

git --version

First-time identity (use your real name and the email tied to GitHub / your host):

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

HTTPS vs SSH: Cloning with HTTPS prompts for credentials; many people use a personal access token as the password. SSH (git@github.com:…) needs an SSH key in ~/.ssh/ and the public key added to your Git host — Cursor’s built-in Git UI works with either once Git is configured.

Windows vs VM: Git on Windows (e.g. Git for Windows) and Git inside the VM are separate installations with separate configs and SSH keys. If you clone only inside the VM, configure Git and keys there.

10.3 Android SDK (beginner-friendly path: Android Studio)

  1. Download Linux Android Studio from the official Android Studio link above.
  2. Extract to something like ~/android-studio (inside the VM disk).
  3. Run the studio installer wizard; let it install the Android SDK to ~/Android/Sdk (default is fine).
  4. In SDK Manager, install at least: Android SDK Platform-Tools, a recent Platform (API level your Flutter project needs), and Command-line Tools.

Add to your shell profile (~/.bashrc or ~/.profile):

export ANDROID_HOME=$HOME/Android/Sdk
export PATH=$PATH:$ANDROID_HOME/cmdline-tools/latest/bin
export PATH=$PATH:$ANDROID_HOME/platform-tools

Then: source ~/.bashrc and test adb version.

10.4 Flutter

  1. Follow the official Linux install page (link above). Typical flow: download the Linux bundle, unpack to ~/development/flutter, add export PATH="$PATH:$HOME/development/flutter/bin" to ~/.bashrc, run flutter doctor.
  2. Accept licenses: flutter doctor --android-licenses

10.5 Gradle

Gradle is pulled automatically by Flutter/Android projects. Caches live under ~/.gradle inside Linux — still on your virtual disk (D: from Windows’ point of view). If disk grows too much, you can occasionally run rm -rf ~/.gradle/caches (only if you understand builds will re-download dependencies).

10.6 Cursor on Ubuntu (guest)

What installing Cursor on Ubuntu does not do: The AI assistant in this Cursor window (on Windows, attached to your repo) cannot run commands inside the VM or “take over” Linux Cursor automatically. Linux Cursor is a separate app. To work in the VM from one editor, use Cursor’s Remote - SSH (or open the Linux folder from a project cloned inside the guest) in a new Cursor window connected to the VM.

Fast path — you already have cursor-linux-x64.deb on Windows under D:\downloads (shared folder name downloads → usually /media/<you>/sf_downloads/ in Ubuntu after Guest Additions + vboxsf group + re-login).

  4. Launch from the app grid (search “Cursor”) or run cursor in Terminal.

10.7 Node.js 20 + npm (carbon-gen & CarbonWMS web)

Both repos are Next.js apps on Node. carbon-gen’s production Docker image uses Node 20 (node:20-bookworm-slim) and is what Coolify builds and runs on your VPS. Align the VM with Node 20 LTS for parity.

Recommended: unpack the official Linux x64 tarball from D:\downloads (see section 14) into e.g. ~/opt/node-v20.20.2-linux-x64 and prepend bin to PATH, or use nvm to install 20.x inside the VM.

Then in each repo: npm ci (or npm install) per project instructions.

10.8 Docker: Desktop (Windows) vs Engine (Linux VM)

Docker Desktop is for Windows and macOS. It is not what you install inside Ubuntu in VirtualBox.

Inside the VM, install Docker Engine + Docker Compose plugin using Docker’s Ubuntu guide (or copy get-docker.sh from D:\downloads). After install, docker compose up -d in carbon-gen and CarbonWMS works like on Windows Desktop.

RAM: Postgres in Docker inside a 6–8 GB VM plus Cursor and Flutter is tight. If the VM swaps heavily, give the VM more RAM (when the host allows) or stop containers when not needed.

Both projects use PostgreSQL 18 images locally:

  • carbon-gen: docker-compose.local.yml → postgres:18-alpine, DB postgres, port 5432.
  • carbon-warehouse-management: docker-compose.yml → postgres:18-alpine, DB carbon_wms, port 5432.

Do not run both compose files at once if both map 5432:5432 unless you change the host port on one stack.

10.8b Docker Desktop (Windows, ~10 GB on D:) → Ubuntu VM

You do not migrate or “copy” Docker Desktop into Ubuntu. Docker Desktop is a Windows/macOS app with its own Linux VM (WSL2 or Hyper-V). Your Ubuntu VirtualBox guest is a separate Linux machine with its own Docker daemon (Docker Engine). Image layers and volumes from Desktop are not the same filesystem as inside Ubuntu — there is no supported drag-and-drop of Desktop’s internal disk into the guest.

What you actually do

  1. In Ubuntu: install Docker Engine + Compose plugin (§10.8, Docker’s Ubuntu docs, or get-docker.sh).
  2. Clone repos inside the VM and run docker compose -f docker-compose.local.yml up -d (carbon-gen) or the CarbonWMS compose file — Docker downloads postgres:18-alpine etc. again into the VM disk. Small download cost; same result as on Desktop.
  3. Database data: If you only used throwaway local Postgres, you need nothing from Desktop. If you have real data you must keep: on Windows, while the old container runs, run pg_dump to a file, copy the file into the VM (shared folder/USB), then psql / pg_restore into the new container. The guide already states this under §15 — Checklist — Docker.
  4. When the VM workflow works: quit Docker Desktop on Windows or uninstall it to reclaim the ~10 GB (use Docker Desktop’s troubleshooting / “Clean / Purge data” if you want to free space before uninstall).
For assistants / agents (copy as context): User has Docker Desktop on Windows consuming ~10 GB (may be on D:). Target state is Docker Engine inside Ubuntu VirtualBox for carbon-gen and CarbonWMS local Postgres. Do not instruct copying Docker Desktop’s VM disk or image store into Linux. Do instruct: install Docker Engine in Ubuntu; docker compose up to re-pull images; optional pg_dump/pg_restore for data migration; then uninstall Docker Desktop on Windows to reclaim space. Production databases live on Coolify, not on either Docker Desktop or the dev VM, unless explicitly testing against a dump.

10.9 Playwright (both repos)

DevDependencies include @playwright/test / playwright. After npm ci, run npx playwright install inside Linux to pull browsers into the VM disk. Expect several hundred MB.

10.10 PowerShell scripts on Linux

carbon-gen’s package.json uses powershell for some scripts (dev, db:local:* helpers, etc.). On Ubuntu, either:

  • Install PowerShell for Linux (Microsoft install guide) and adjust paths if needed, or
  • Invoke the underlying tools directly (e.g. npm run dev:raw / docker compose -f docker-compose.local.yml …) instead of the PowerShell wrapper scripts.

CarbonWMS dev uses node scripts/run-next-dev.mjs — no PowerShell required.

11. Shared folders — stay off C:

Best for your goal: keep code inside the VM (~/dev/...) and use Git to push/pull. No shared folder required.

If you must share files with Windows:

  1. Create D:\DevShared\ on Windows.
  2. VirtualBox → VM Settings → Shared Folders → add folder path D:\DevShared, name devshared, enable Auto-mount.
  3. In Ubuntu, Guest Additions must be working. The share often appears under /media/sf_devshared (may need adding your user to the vboxsf group — search “VirtualBox vboxsf group Ubuntu”).
Do not add a shared folder pointing at C:\ if your objective is to keep C: from growing. Point shares only at D:\….

12. When something goes wrong

SymptomWhat to check
“VT-x is not available” / virtualization error Enable virtualization in BIOS. Ensure no conflicting hypervisor feature blocks VirtualBox on your Windows edition.
VM is extremely slow Lower display resolution; ensure Guest Additions installed; reduce VMs RAM if host is swapping; close Windows apps.
Host freezes when starting Android emulator inside VM Expected on limited RAM. Use a physical device with USB debugging, or build without running an emulator inside the nested VM.
flutter doctor cannot find Android SDK Confirm ANDROID_HOME and PATH lines; reopen terminal; SDK installed via Studio or cmdline tools.
Shared folder empty or permission denied Guest Additions installed? User in vboxsf group? Correct host path on D:?
Virtual disk fills up Increase VDI size in VirtualBox Media Manager (and grow partition inside Linux) or prune ~/.gradle / old SDK images in Android Studio SDK Manager.
Black screen after Ubuntu install Increase video memory; try disabling 3D acceleration in VM display settings (trade-offs apply).
docker compose not found in VM Install Docker Engine and the compose plugin from Docker’s Ubuntu docs; log out/in after adding your user to the docker group.
Port 5432 already in use in VM Only one stack can own host port 5432; stop the other compose project or change the published port in one docker-compose file.
git push / clone fails (auth) Set user.name / user.email; for HTTPS use a token; for SSH add ~/.ssh key to GitHub/GitLab and test ssh -T git@github.com.

13.0 Coolify — production hosting (carbon-gen & CarbonWMS)

Coolify is the operational home for both Carbon web applications in production: your VPS runs the Coolify control plane, builds images from Git, runs containers behind Traefik (TLS, routes), and attaches managed PostgreSQL services. That environment is not the same as the Ubuntu VM’s local docker compose — the VM is for development; Coolify is for what customers and integrations hit on the public internet.

carbon-gen (e.g. app.shopcarbon.com):

  • Deploy: npm run deploy:coolify (see scripts/deploy-coolify.mjs); optional .coolify-deploy.local.json (gitignored) for webhook URL + API token; setup helper npm run deploy:coolify:setup.
  • Database: Production Postgres is the Coolify-linked service; app env uses DATABASE_URL, COOLIFY_DATABASE_URL, and related vars (see lib/sqlDb.ts, lib/authRepository.ts).
  • Health: Point Coolify / Docker healthchecks at GET /api/health (fast, no DB). Full ops notes: docs/coolify-runbook.md.
  • Scheduled work: Cron-style jobs can run as Coolify scheduled tasks or external HTTPS cron hitting public routes (see docs/CRON_SETUP.md).
  • Object storage: Cloudflare R2 (S3-compatible) remains a separate service; only that CF surface is required for media, not Workers.

carbon-warehouse-management (CarbonWMS): Same Coolify + Postgres + container pattern on your stack — one Coolify app (or project) per service, healthcheck on a liveness-style HTTP path, env for DB URL and secrets. Flutter mobile builds still happen on your dev machine or CI; the Next/API backend ships like carbon-gen.
